# TEST-REPORT-002: E2E walkthrough, auth / workspace / members / invitations

## 1. Verdict

No application bug found. Four small UI/UX warnings (section 3); all four were fixed afterwards and re-checked in the browser (section 3a).

- Commit `6f8bf49` plus many uncommitted changes. core-api (8080), web (3000) and ai-service (8000) were up. Nothing was rebuilt.
- I did not check whether the running core-api image contains the uncommitted core-api changes.
- Screenshots are in `artifacts/testing/e2e-2026-11-21/` (gitignored, so the images show only on this machine).

## 2. What was run

| Run | Result |
|---|---|
| Suite `01-access-and-publishing` | 13 passed |
| Suite `02-members-and-departments` | 9 passed |
| Suite `04-page-health` (4 roles, desktop and phone) | 8 passed |
| About 70 HTTP checks by script (not committed) | 0 app bugs |

Nine checks first showed FAIL. All were my wrong expectation or a script problem, not an app bug (for example suspend returns `204`, not `200`; the `Secure` cookie is not kept over plain http).

What the HTTP checks proved, in plain words:

| Area | Proven |
|---|---|
| Auth | No token, bad token or wrong origin is refused. Refresh gives a new token each time. Reusing an old token after 10 s kills the whole session. Logout really ends the session. A suspended member cannot sign in to the workspace. |
| Workspace | Only an owner renames or deletes. Names of 0 or 300 characters are refused. A personal workspace cannot be deleted or left. A deleted workspace is gone (`404`). |
| Invitation | Only owner or admin invites. Bad email or role is refused. Duplicate or existing member is `409`. Wrong account is `409`, revoked invite is `410`. The pending list never shows the token. |
| Member | The last owner cannot leave or be demoted. An admin cannot touch an owner. A member cannot suspend anyone. |

## 3. Findings from the browser

### F1. Phone: Members table hides its actions

On a 390 px phone the table scrolls sideways. Role, Status and the Edit / Suspend / Remove buttons are off-screen and nothing hints at them. Expected: a visible hint, or one card per member.

![Members at 390 px](../../../artifacts/testing/e2e-2026-11-21/members-admin-390.png)

### F2. Wrong account on the invite page: unhelpful message

The message says "sent to a different email address" but does not say which account is signed in and offers no way to switch. Expected: show the current account and a "Sign out and use another account" button.

![Invite, wrong account](../../../artifacts/testing/e2e-2026-11-21/invite-mismatch-390.png)

### F3. Desktop: action buttons wrap

At 1280 px, Edit and Suspend sit on one line and Remove drops below, so rows have uneven height. Expected: one line.

![Members at 1280 px](../../../artifacts/testing/e2e-2026-11-21/members-admin-1280.png)

### F4. Google button text is Vietnamese

The button reads "Đăng nhập bằng Google". Google picks the language from the browser; UI copy is meant to be English. Accept it as Google-controlled, or set the locale.

![Login at 1280 px](../../../artifacts/testing/e2e-2026-11-21/login-1280.png)

## 5. Notes (by design, not bugs)

- A suspended member's already-issued access token works until it expires (up to 15 minutes), because endpoints do not re-read the membership (core-api design §5.6).
- Anonymous `/login` logs one `401` on `/auth/refresh` in the console: it is the session check.

## 6. Not checked

- Real Google sign-in (only dev login), expired invitation (7 days), employee-code conflict, archived department on invite.
- Arrow-key use of tabs and selects; screens of other roles at 390 px; real access-token expiry in the browser; ai-service errors; chat; documents and ingestion.
- Chromium only. No Docker-only suites.

## 7. Proposed scenarios

1. Reusing a refresh token after the grace window ends the session.
2. The wrong-account invite message names the signed-in account and the button keeps the link (F2 is fixed, no test yet).
3. A suspended member is refused at the next refresh.
4. The last owner cannot leave or be demoted from the Members screen.
5. Members actions stay reachable at 390 px (F1 is fixed, no test yet).
